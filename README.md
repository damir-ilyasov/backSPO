Целью практической работы является разработка веб-приложения для аренды складских ячеек с backend-частью на REST API. Приложение позволяет клиентам просматривать доступные ячейки на складах и оформлять их аренду, а администраторам — управлять складами, ячейками и договорами аренды.
Задачи backend-части:
- спроектировать доменную модель предметной области;
-	спроектировать структуру базы данных (ER-диаграмма);
-	реализовать REST API с разделением на слои согласно принципам Clean Architecture;
-	реализовать аутентификацию и авторизацию с разграничением ролей (гость, клиент, администратор);
-	покрыть основные сценарии (CRUD по складам, ячейкам и договорам аренды, смена статуса ячейки, оформление и расторжение аренды);
-	выполнить тестирование основных сценариев работы API.
-	В рамках проекта backend является самостоятельной частью, взаимодействующей с frontend исключительно по REST API.
2. Обзор литературы
При выполнении backend-части проекта были изучены и проанализированы источники по проектированию архитектуры веб-приложений, работе с базами данных и построению REST API.
Основные направления анализа:
-	принципы Clean Architecture и разделение приложения на слои (Domain, Application, Infrastructure, Presentation);
-	подходы к проектированию REST API и выбору HTTP-методов, кодов ответов, структуры маршрутов;
-	проектирование реляционных баз данных и построение ER-диаграмм;
-	использование ORM Entity Framework Core и миграций Code First;
-	аутентификация и авторизация на основе ASP.NET Identity и JWT;
-	применение паттерна Result для обработки доменных ошибок без исключений;
-	использование value object'ов для проверки инвариантов домена.
Также были рассмотрены материалы по построению диаграмм: UseCase, диаграмма классов (UML), ER-диаграмма и UserStoryMap, что позволило согласовать backend-реализацию с общей проектной документацией команды.
Анализ литературы показал, что для данного проекта оптимальным является монолитная Clean Architecture с PostgreSQL и EF Core, поскольку это обеспечивает независимость доменной логики от инфраструктуры и упрощает дальнейшее развитие проекта.
3. Методология
Backend реализован на C# (.NET 8) с использованием монолитной Clean Architecture. Решение разделено на слои:
-	Domain — доменные сущности, value object'ы, интерфейсы репозиториев, доменные исключения и правила. Не зависит ни от одного другого слоя.
-	Application — сценарии использования (хендлеры), DTO запросов/ответов, интерфейсы репозиториев для конкретных операций.
-	Infrastructure — реализация репозиториев на EF Core, конфигурации сущностей, подключение к PostgreSQL, интеграция ASP.NET Identity и JWT.
-	Presentation (Api) — контроллеры, маршрутизация, Swagger, middleware.
Для представления результата операций вместо исключений используется паттерн Result (библиотека CSharpFunctionalExtensions): каждый доменный метод и хендлер возвращает Result с успешным значением либо доменной ошибкой (Error) с явным типом — Validation, NotFound, Conflict, Failure. Ошибки транслируются в HTTP-коды на уровне контроллеров.
Идентификаторы сущностей и часть атрибутов оформлены как value object'ы (например, WareHouseId, StorageId, SizeOfStorage) с приватными конструкторами и статическими фабричными методами Create, что позволяет проверять инварианты в момент создания объекта, а не постфактум.
База данных — PostgreSQL, поднимается локально через Docker Compose. Миграции выполняются средствами EF Core (Code First).
Для валидации входных данных используются FluentValidation (на уровне Application) и ручная валидация внутри доменных методов Create/Update (как основная защита инвариантов домена).
4. Создание макетов
В рамках backend-части под «макетами» понимаются проектные артефакты, определяющие структуру данных и контракты API: ER-диаграмма, доменная модель и спецификация REST API.
4.1. ER-диаграмма и проектирование базы данных
В базе данных выделены следующие основные сущности:
-	Warehouse (склад) — Id, Name, Description, Address, Floor. Содержит набор ячеек.
-	StorageCell (складская ячейка) — Id, WarehouseId (FK), Number, Width/Height/Depth, SizeCategory, Price, Floor, Status (Free/Booked). Принадлежит одному складу.
-	RentalAgreement (договор аренды) — Id, StorageCellId (FK), ClientId (FK на пользователя), StartDate, EndDate, TotalPrice.

Связи:
-	Warehouse (1) — StorageCell (N): один склад содержит множество ячеек.
-	StorageCell (1) — RentalAgreement (N): одна ячейка за время своего существования может иметь множество договоров аренды (не одновременно, а последовательно — после освобождения ячейки её можно сдать снова).
-	Пользователь (1) — RentalAgreement (N): один клиент может оформить несколько договоров.
Отдельно поле Status у StorageCell хранит текущее состояние ячейки (свободна/забронирована) — это денормализованное, но быстрое поле для проверки доступности без обращения к истории договоров.
Для аутентификации используется ASP.NET Identity: таблицы пользователей и ролей создаются автоматически (AspNetUsers, AspNetRoles, AspNetUserRoles), договор аренды хранит ссылку на Id пользователя-клиента.
4.2. Спецификация REST API
Аутентификация:
-	POST /auth/register — регистрация клиента
-	POST /auth/login — вход, получение JWT
Склады (Warehouse):
-	POST /warehouse — создать склад (администратор)
-	GET /warehouse — список складов (доступно всем)
-	GET /warehouse/{id} — карточка склада (доступно всем)
-	PUT /warehouse/{id} — полное обновление (администратор)
-	PATCH /warehouse/{id} — частичное обновление (администратор)
-	DELETE /warehouse/{id} — удаление (администратор)
Складские ячейки (StorageCell):
-	POST /storagecell — создать ячейку (администратор)
-	GET /storagecell — список ячеек (доступно всем)
-	GET /storagecell/{id} — карточка ячейки (доступно всем)
-	PUT /storagecell/{id} — полное обновление (администратор)
-	PATCH /storagecell/{id} — частичное обновление (администратор)
-	DELETE /storagecell/{id} — удаление (администратор)
-	POST /storagecell/{id}/reserve — забронировать ячейку
-	POST /storagecell/{id}/release — освободить ячейку (администратор)
Договоры аренды (RentalAgreement):
-	POST /rentalagreement — оформить аренду (клиент)
-	GET /rentalagreement — список договоров
-	GET /rentalagreement/{id} — карточка договора
-	PUT /rentalagreement/{id} — изменение сроков/стоимости (продление)
-	DELETE /rentalagreement/{id} — расторжение договора, автоматически освобождает ячейку
4.3. Роли и права доступа
В системе выделены три уровня доступа:
Гость (неавторизованный пользователь): просмотр списка складов и ячеек, просмотр карточки конкретной ячейки. Не может оформлять аренду.
Клиент (авторизованный пользователь): всё то же самое, что и гость, плюс оформление аренды свободной ячейки, просмотр и расторжение собственных договоров.
Администратор: всё то же самое, что и клиент (включая возможность самому арендовать ячейку), плюс создание, изменение и удаление складов и ячеек, принудительное освобождение ячейки, просмотр и расторжение любых договоров аренды.
Роль «гость» реализована не как отдельная Identity-роль, а как отсутствие авторизации: соответствующие эндпоинты помечены как общедоступные, остальные — защищены атрибутом авторизации с проверкой роли.
5. Сравнительный анализ инструментов
СУБД
-	PostgreSQL — выбран основной вариант. Бесплатный, открытый исходный код, хорошая поддержка в EF Core (провайдер Npgsql), удобно поднимается в Docker.
-	MS SQL Server — более тяжёлая лицензионная модель для промышленного использования, но так же хорошо поддерживается EF Core; рассматривался как альтернатива.
-	MySQL — рассматривался, но слабее поддержка некоторых типов данных и меньше распространён в связке с .NET по сравнению с PostgreSQL.

ORM / доступ к данным
-	Entity Framework Core — выбран основной инструмент. Позволяет описывать модель через Fluent API, автоматически генерировать миграции, поддерживает value conversions для value object'ов.
-	Dapper — более быстрый, но требует писать SQL вручную и не даёт того уровня абстракции, который нужен для Clean Architecture с богатой доменной моделью.
-	Raw ADO.NET — избыточно трудозатратно для сроков и масштаба проекта.

Аутентификация
-	ASP.NET Identity + JWT — выбранный вариант. Готовая реализация хранения пользователей, хэширования паролей, управления ролями, в сочетании с JWT даёт stateless-авторизацию, удобную для REST API.
-	Cookie-based авторизация — не подходит, так как backend и frontend разделены и общаются исключительно по REST API.
-	Самописная система пользователей — отклонена как избыточная работа при наличии готового, проверенного решения.

Валидация
-	FluentValidation — используется для валидации входных DTO на уровне Application.
-	Ручная валидация внутри доменных методов Create/Update — используется как основная защита инвариантов домена (независимо от того, что происходит выше по стеку).

Инструменты документирования API
-	Swagger / OpenAPI — используется для автоматической генерации документации и ручной проверки эндпоинтов.
-	Postman — применялся для ручного тестирования запросов и проверки сценариев.
6. Пользовательское тестирование
В рамках backend-части под пользовательским тестированием понимается проверка API со стороны потребителей: frontend-разработчика и участников команды, а также ручное и автоматизированное тестирование сценариев.
6.1. Проверяемые сценарии
Были протестированы следующие группы сценариев:
1.	Аутентификация и авторизация
-	регистрация нового клиента;
-	вход и получение JWT;
-	доступ к защищённым эндпоинтам без токена (должен быть запрещён);
-	доступ к административным эндпоинтам под ролью клиента (должен быть запрещён);
-	доступ к административным эндпоинтам под ролью администратора.
2.	CRUD по складам и ячейкам
-	создание, чтение, обновление и удаление склада администратором;
-	создание, чтение, обновление и удаление ячейки администратором;
-	проверка доступности списков и карточек для гостя.
3.	Аренда
-	оформление аренды свободной ячейки клиентом;
-	попытка аренды уже занятой ячейки (должна возвращаться доменная ошибка Conflict);
-	расторжение договора и автоматическое освобождение ячейки;
-	бронирование и освобождение ячейки администратором.
4.	Валидация и обработка ошибок
-	передача некорректных DTO (проверка FluentValidation);
-	проверка соответствия доменных ошибок HTTP-кодам (Validation → 400, NotFound → 404, Conflict → 409, Failure → 500).
6.2. Обратная связь
По результатам тестирования были выявлены и устранены следующие замечания:
-	уточнены коды ответов для некоторых ошибок (например, конфликт при повторной аренде);
-	добавлены проверки инвариантов на уровне value object'ов, чтобы некорректные данные не попадали в базу;
-	скорректирована структура DTO для удобства использования на frontend;
-	проверено, что расторжение договора действительно освобождает ячейку и она снова доступна для аренды.
Тестирование подтвердило, что API соответствует заявленным сценариям и ролям, а frontend может быть реализован независимо на основе спецификации.

Архитектура позволяет независимо развивать бизнес-логику и инфраструктуру: смена СУБД или способа хранения данных не затрагивает доменный слой и сценарии использования. Использование паттерна Result и value object'ов обеспечивает явную обработку ошибок и защиту инвариантов домена.

# Backend (Аренда складских ячеек)

Backend на ASP.NET Core 8, PostgreSQL, Clean Architecture.

## Стек

- .NET 8
- PostgreSQL 16
- Entity Framework Core (Npgsql)
- ASP.NET Identity + JWT (в HttpOnly-куке)
- CSharpFunctionalExtensions (Result-паттерн)
- Swagger / Swashbuckle

## Структура решения

```
ProjectOne/                    — Api (контроллеры, Program.cs, Swagger)
ProjectOne.Application/        — сценарии использования, DTO, интерфейсы репозиториев
ProjectOne.Domain/             — сущности, value object'ы, доменные правила
ProjectOne.Infrastructure/      — EF Core, репозитории, Identity, JWT
```

## Требования

- .NET 8 SDK
- Docker Desktop (для PostgreSQL)
- dotnet-ef (`dotnet tool install --global dotnet-ef`, если ещё не установлен)

## 1. Поднять базу данных

В корне решения лежит `docker-compose.yml`:

```bash
docker compose up -d
```

Проверить, что контейнер поднялся:

```bash
docker compose ps
```

База будет доступна на `localhost:5432`, пользователь `postgres`, пароль `postgres`,
база данных `projectone` (см. `docker-compose.yml`, при необходимости поменяйте).

## 2. Настроить конфигурацию

В `ProjectOne/appsettings.Development.json` (создайте, если его нет) укажите:

```json
{
  "ConnectionStrings": {
    "Db": "Host=localhost;Port=5432;Database=projectone;Username=postgres;Password=postgres"
  },
  "Jwt": {
    "Issuer": "ProjectOne",
    "Audience": "ProjectOneClients",
    "Key": "замените-на-свой-секретный-ключ-минимум-32-символа",
    "ExpiresMinutes": 120
  }
}
```

## 3. Применить миграции

Миграции применяются автоматически при старте приложения (см. `Program.cs`,
`db.Database.MigrateAsync()`). Ручной запуск, если нужно применить их отдельно:

```bash
dotnet ef database update -p ProjectOne.Infrastructure -s ProjectOne
```

Создание новой миграции после изменения сущностей:

```bash
dotnet ef migrations add НазваниеМиграции -p ProjectOne.Infrastructure -s ProjectOne
```

## 4. Запустить API

```bash
dotnet run --project ProjectOne
```

По умолчанию API поднимется на `https://localhost:44373` (или на порт, указанный
в `ProjectOne/Properties/launchSettings.json`).

Swagger UI: `https://localhost:44373/swagger`

## 5. Аутентификация

Токен выдаётся в виде `HttpOnly`-куки `access_token` после `POST /auth/login` или
`POST /auth/register` — фронтенд не работает с токеном напрямую, достаточно
отправлять запросы с `credentials: 'include'` (fetch) или `withCredentials: true`
(axios).

Выход: `POST /auth/logout` - удаляет куки.

## 6. CORS

Список разрешённых origin'ов фронтенда задан в `Program.cs` (`AddCors`). При смене
порта/адреса фронтенда - обновите `WithOrigins(...)`.

## Возможные проблемы при запуске

- **Postgres не пускает по паролю** — убедитесь, что контейнер поднят с тем же
  паролем, что указан в строке подключения; при смене пароля в `docker-compose.yml`
  для уже созданного контейнера нужно пересоздать volume
  (`docker compose down -v && docker compose up -d`).
- **Не собирается миграция из-за FluentValidation.AspNetCore** — пакет не используется
  в проекте, валидация выполняется через `FluentValidation` + ручной вызов в
  хендлерах.
- **CORS-ошибка в браузере при логине с фронта** — проверьте, что адрес фронтенда
  указан в `WithOrigins`, а запрос идёт с `credentials: 'include'`.
